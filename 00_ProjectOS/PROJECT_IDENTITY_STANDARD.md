# ProjectOS — PROJECT IDENTITY STANDARD

> 项目身份不是本轮任务说明，而是“换一个 AI、换一个会话、换一期内容之后，这个项目仍然必须像它自己”的长期约束。

## 1. 每个长期项目必须回答四件事

每个 `PROJECT_HOME` 必须包含：

1. **核心体验 / Core Experience**  
   观众或用户连续接触这个项目时，稳定获得什么体验。

2. **识别特征 / Signature Traits**  
   3–7 个真正区分该项目的角色、视觉、叙事、剪辑、交互或技术语言。

3. **可变化区 / Allowed Variation**  
   每一期/每一版可以自由探索什么，避免把项目冻结成模板。

4. **不可无声变化 / Protected Identity**  
   哪些变化会让项目“不再像自己”；若改变，必须显式进入 `CHANGES`。

## 2. 身份与实现细节分离

写入 PROJECT IDENTITY 的内容应满足至少一项：
- 明确由用户确认是长期方向；
- 已跨多次制作验证有效；
- 改变它会显著改变观众/用户对项目的预期；
- 它是项目架构、视觉协议或叙事承诺的一部分。

以下内容通常不要写成永久身份：
- 某一集的具体剧情；
- 当前临时文件名；
- 可能很快被替换的版本号；
- 一次性的参数试验；
- 未经验证的灵感。

这些进入 `ACTIVE / DELTA / HANDOFF`。

## 3. 母项目继承

单集、短期 sprint、软件小版本默认继承母项目全部 PROJECT IDENTITY。

例如：
`CT-02 EP08` 默认继承 `CT-02 结束乐队×Minecraft` 的角色、喜剧、Minecraft进度与动画语言。

子任务只需写：
- `DELTA`：本轮新增/不同之处；
- `TASK`：本轮唯一目标；
- `ACCEPTANCE`：验收标准；
- `CHANGES`：是否改变母项目长期规则。

若 `CHANGES = none`，不得因为新会话/新模型而重新设计母项目风格。

## 4. 身份变更协议

任何长期规则变化必须写：

```text
CHANGES:
- WHAT: 改了什么
- WHY: 为什么改
- EVIDENCE: 来自用户决定、数据、QA或实际制作的什么证据
- IMPACT: 会影响哪些后续内容/文件/兼容性
```

禁止静默修改。

如果只是实验，先写到 `DELTA`，经过至少一次真实制作/测试后再决定是否升格为身份规则。

## 5. AI 接管行为

新 ChatGPT/Codex/Work 会话接管项目时：
1. 先读 `PROJECT_HOME` 的 PROJECT IDENTITY；
2. 将其视为默认约束，不重新发明；
3. 再读本轮 DELTA / TASK；
4. 优先保护已经成功的部分；
5. 若发现身份规则互相冲突，报告冲突，不自行选择性遗忘；
6. 结束时只回写新事实和真正发生的规则变化。

## 6. 判断标准

一个 PROJECT_HOME 合格的最低标准是：

> 一个完全没读过历史聊天的 AI，只读这个文件，就能回答：
> - 这个项目是什么？
> - 为什么它值得继续？
> - 它看起来/工作起来应该是什么感觉？
> - 什么可以创新？
> - 什么不能随便改？
> - 当前只该做哪一件事？

答不出来，则项目入口仍然不完整。
