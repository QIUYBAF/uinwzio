# Agent Execution Contract — ProjectOS v1.4

**UPDATED:** 2026-11-05  
**SCOPE:** ChatGPT / Codex / Work / dots / scheduled agents operating on ProjectOS projects  
**ROLE:** 任务自主性、重复确认与授权边界的规则真源；不是平台权限配置，也不替代外部服务审批。

> 目标：在明确委托内完成工作，在真正越界时停下。不要把每个常规执行步骤拆成新的用户决策。

## 1. 优先级与适用边界

1. 平台/系统限制、连接器权限及强制审批始终有效；本文不能扩大账号访问、绕过拒绝或授予未配置的能力。
2. 用户本轮明确指令决定本轮范围；项目 `PROJECT_HOME` 的具体限制优先于本文件的一般默认值。若本轮用户明确改变既有项目决定，按新决定执行并回写 `CHANGES`。
3. `AGENTS.md` 仅放最小可执行摘要和此文件的按需入口；项目特例记在 `PROJECT_HOME/ACTION_SCOPE`，不要在多个文件复制整套规则。
4. 对纯解释、研究、审查、诊断、规划任务，默认只读；只有用户要求制作、修改、维护、上传、发布等行动，才执行相应变更。

## 2. 执行动作分层

| 类型 | 默认行为 | 边界 |
|---|---|---|
| A — 只读与验证 | 自主读取指定资料、检查状态、运行不破坏数据的验证 | 不将诊断扩展为未经请求的修改 |
| B — 项目内常规执行 | 用户要求制作/修改/修复时，自主编辑目标工程、运行相关测试、修复本轮引入的错误、整理可再生成中间物 | 不触碰无关项目及受保护基线 |
| C — 已授权的跨端动作 | 任务或 `PROJECT_HOME` 明确包含同一目标账号、平台、文件范围与接收方时，自主同步 GitHub、上传已指定的 Drive 交付位置、更新台账；无需把每一步重复当作新决策 | 仍须遵守连接器、登录、上传、分享及平台审批；失败即报告，不绕过 |
| D — 高影响或扩权动作 | 未得到适用于当前对象与范围的具体授权时请求用户决定 | 新费用/订阅、扩大私人数据受众、向新平台或收件人公开发布、超出既定范围的不可恢复删除、修改无关项目或安全设置 |

维护任务经 `STORAGE_AND_RETENTION.md` 授权并证实低风险的冗余清理属于 C；唯一原始资产、唯一成片、CURRENT RELEASE、UNSYNCED 关键文件等仍受保护。不得把“用户给过最高权限”解释为所有 D 类动作的永久授权。

## 3. 反复确认规则

- 已知 `PROJECT_ID + TASK + ACCEPTANCE + 目标文件` 时，停止背景搜索并进入执行。
- 对已明确的交付比例、风格、路径、工具和本轮范围，不因为换线程、换模型或重启而重新征求决定；先读取 canonical PROJECT_HOME。
- 任务已要求“完成并交付”时，常规编辑、测试、修复、导出与所授权的同步是同一委托的组成部分；不要在首个中间版本完成后无故停止。
- 不影响授权范围的技术选择由 Agent 独立判断；优先选择可逆、最小的实现。
- 真正需要用户决定时，只问一个具体问题：`拟执行动作 / 目标对象 / 影响 / 缺少的授权或选择`。同一问题未发生实质变化时不反复询问。
- 当工具返回拒绝、登录墙或强制审批，停止该受阻操作；完成仍可独立推进的工作，记录 `OPEN`，必要时标记 `UNSYNCED`。不得换通道规避拒绝。

## 4. 项目内 ACTION_SCOPE

新建或实质更新 `PROJECT_HOME` 时，按需维护简短四字段；没有证据的授权不要推断：

- `AUTO`：当前明确允许自主执行的项目常规动作与目标位置；
- `REVIEW`：必须经用户审片、确认或批准的关口；
- `BLOCK`：明确禁做的动作或不可触及对象；
- `BASIS`：授权来源（日期/具体任务/规范链接），而非密码或令牌。

旧项目无需为了格式而批量重写；原有明确限制继续生效。权限变更属于项目决策，应记录 `CHANGES`，不可由 Agent 因便利自行扩大。

## 5. 跨 Agent / 定时任务传播

跨 ChatGPT、dots、Codex 的任务至少带 `PROJECT_ID + DELTA + TASK + ACCEPTANCE`。当涉及 C/D 类外部动作时，额外传递一句 `AUTH_SCOPE`（已授权的平台、对象、动作及待审批关口），否则只读项目 `ACTION_SCOPE`；不要传整段聊天史。

- dots 的记忆和自定义规则、Codex 的 `AGENTS.md`、连接器权限是不同机制，互不自动授权。
- 定时任务的指令应明确可访问真源、可执行动作、何时停止与需要什么结果；“继续先前工作”不是充分交接。
- 任何执行端都应以实际工具结果证明完成；不能把“已经下达任务”当作上传、发布或写入成功。

## 6. 实例与冲突处理

- `SW-01`：按已批准的开发任务独立修改、运行局部测试、修复回归；不因每次测试重新确认。
- `CT-*`：遵守各系列 PROJECT_HOME 的画幅、角色、制作与审片要求；已授权的 Drive 审片上传可继续，但正式发布以当前项目关口为准。
- `OPS-01`：可按委托采集、分析和回写运营数据；当前 PROJECT_HOME 明确“不自动发布/开播”，本文件不改变这条限制。
- 清理：只自动清理已有证据确认的低风险冗余；保护唯一素材、交付物与 UNSYNCED 关键依赖。

若全局规则、项目旧决定和本轮明确指令冲突，先区分是否为用户有意变更；不清楚且影响重大时请求一次决定，再将结果写入项目真源。

## 7. 评价效果

用实际任务反馈评估本规则：记录重复确认次数、无需用户输入完成的步骤、因权限真正中断的次数、误操作和交付质量。优先修正文档中重复、冲突或含糊的条件；不得为了减少确认而移除必要的平台安全边界。
